# 视觉接入代码：从哪里看、每一步做什么

这份说明对应三个准备模块：速度指令诊断、视觉状态校验、离线控制预览。本轮整理这些模块的代码结构和命名，协议、阈值和原来的处理行为保持一致。

后续边界修复见 [边界问题与验证](VISION_BOUNDARY_REVIEW_20261111.md)：补充时钟回退、事件副本、外参不可变和姿态小角度计算。本文末尾的差分结果对应此前的纯重构，当前实现另有这几项有意的行为修复。

最新整体验证和原始 Odometry 适配器整理见 [工程审查](FC01_ENGINEERING_REVIEW_20261111.md)。该轮另修复配对超时、适配器参数和退出、安装完整性、长期审计缓存及生产视觉算术边界；没有打开视觉飞行开关。

## 先分清两种速度

| 名称 | 例子 | 来源 |
| --- | --- | --- |
| 实际速度 | 飞机当前向前飞 0.1 m/s | `Odometry`，视觉估计结果 |
| 目标速度 | 希望飞机向前飞 0.3 m/s | `VelocityCommand`，视觉制导要求 |

它们分别存储。只有同时拿到可信实际状态和有效目标，才有计算误差的条件。目标不能填进实际速度字段，消息收到了也不等于飞机开始执行。

当前可以单独运行的两个节点是：`vision_odometry_adapter.py` 把 `Odometry + VisionHealth` 转成 `VisionState`；`velocity_command_diagnostic.py` 订阅目标速度并保存诊断。`vision_state_validation.py` 是额外的纯计算校验工具，`velocity_command_input.hpp` 是额外的离线预览工具，两者尚未自动串成生产闭环。正式服务继续保持 `visual_navigation_enabled=false`。

## 先看原始实际状态如何转换

文件：`native/tools/vision_odometry_adapter.py`。先读 `AdapterConfig` 和 `ConvertedState`，再读 `convert_odometry()`。配置明确来源、原始世界/机体坐标、机体外参和世界对齐；结果里的每个有效位都代表实际检查，不能由默认数值推断。

`convert_odometry()` 先检查测量时间及配套健康合同，再计算坐标和姿态，随后处理位置、角速度与杆臂速度，最后决定哪些实际状态有效。非零杆臂下，传感器旋转会产生额外线速度，需要实测角速度修正。原始协方差还没有完整转换，所以输出保留未知值并清除对应有效位。

`StampPairBuffer` 只拼完全相同 stamp 的两半消息。每次回调先过期旧项，迟到的一半不能绕过配对超时；同回调若同时产生撤销和正常新帧，撤销先返回。`GuardedOdometryAdapter` 另外核对原始两个话题各自的真实发布者数量，不能只看输出话题有一个适配器就认定上游单一来源。

文件最后的 `main()` 才导入 ROS 并建立节点。启动参数只读，改参数需重启这个独立适配器；停止它不执行解锁或飞行模式切换。

## 1. 看目标速度怎么接收

文件：`native/tools/velocity_command_diagnostic.py`。从 `Receiver.receive()` 开始读；ROS 回调只负责提供消息、当前时钟和发布者数量。

处理顺序：

1. 观察本机时钟，检查旧候选是否已经过期。
2. 读取新消息的字段，检查版本、序号、时间、来源、坐标系和速度。
3. 识别来源或发送方 reset 的变化，再检查重复、乱序和时间是否推进。
4. 只有可信消息才推进历史记录；决定保存当前候选还是撤销它。
5. 保存这次原始观察和事件，错误单独保留。

第一步必须在替换缓存前执行。例如上一帧已经断流，随后正常新帧到来：新帧可以恢复诊断候选，之前发生的断流仍要留下记录。

`Receiver.snapshot()` 给出当前诊断。三个容易混淆的名字：

| 字段 | 含义 |
| --- | --- |
| `last_message` | 最近收到的消息，可能非法，也可能还没收到而为 null |
| `historical_last_accepted_message` | 最近一次通过检查的历史消息，时间可能已经过去很久 |
| `current_candidate` | 此刻满足已配置诊断条件的候选；条件不足或失效时为 null |

`accepted=true` 只表示通过当时启用的接收检查。默认阈值未配置、来源未绑定时，不能由此得到 `cache_usable=true`。即使候选可用，`control_authority` 仍是 false。

`DiagnosticWriter` 负责有大小限制的日志和快照。`finalize_diagnostic()` 负责正常退出前保存待写异常，并将最后快照标记为停止；它不会在 ROS 上下文关闭后继续查询时钟或网络图。

## 2. 看飞机自身状态怎么检查

文件：`native/tools/vision_state_validation.py`。从 `Validator.receive()` 开始读，再看 `current()`。

输入必须是测量时间完全配对的 `Odometry` 和 `VisionHealth`。处理包括：

1. 观察时钟及旧缓存年龄，记录已经发生的过期。
2. 检查来源、地图/重定位周期及估计器 reset。
3. 按显式时间对应关系映射测量时间。
4. 检查原始协方差，调用原 Odometry 转换公式，再检查跟踪质量及位置、速度、姿态连续性。
5. 全部通过后，提交新的可信基线和当前缓存；否则记录拒绝原因。

`_baseline` 是最后可信状态，用来判断下一帧是否跳变。`_cache` 是当前尚未过期的状态。拒绝一帧或缓存过期，不会删除可信基线，否则“异常位置出现两次”就可能被错误地当成正常。

代码里的 epoch 可以理解成“一个估计周期的身份”：来源、坐标、reset 和重定位标识共同描述它。新的明确周期可以重建位置连续性基线；退役周期重新出现会被拒绝，防止旧地图数据回放。reset 可以让序号重新开始，但不能使同一已确认测量时钟倒退。

协方差描述估计的不确定性。只有明确声明矩阵有效时才检查：有限数、非负方差、对称、半正定，以及已配置的方差上限。半正定意味着任意线性方向的方差都不能为负，不能只检查六个对角线。这里检查原始矩阵；输出没有宣称已完成协方差的坐标和杆臂变换。

## 3. 看目标如何变成离线预览

文件：`native/src/jikl_fc01_system/include/jikl_fc01_system/velocity_command_input.hpp`。先读 `Target`、`Policy`、`Preview`，再读 `Session` 的 `state()`、`command()`、`preview()`。

- `state()` 保存实际状态：世界系速度、姿态、来源和测量时间。
- `command()` 保存目标：机体系速度、独立的来源和发送方 reset。
- `preview()` 检查两者的新鲜度及采样偏差，再计算预览。

计算顺序如下：

```text
目标速度（机体 FRD）
    ↓ 用对应姿态旋转完整三维向量
目标速度（世界 NED）
    ↓ 限制水平合速度和垂直速度
速度误差 = 目标速度 − 实际速度
    ↓ 水平误差乘以速度增益
水平加速度
    ↓ 加速度上限和倾角上限
姿态预览
```

FRD 是前、右、下；NED 是北、东、下。飞机有横滚或俯仰时，机体“前方”可能包含世界垂直分量，因此不能只用偏航角旋转水平速度。四元数采用 `[w, x, y, z]` 顺序。

例如旋转后目标北向速度是 0.3 m/s，实际北向速度是 0.1 m/s，误差就是 0.2 m/s，再乘外环增益得到加速度。零目标速度遇到非零实际速度时会得到制动方向；它并不自动提供位置锁定。

计算的中间结果在限幅前检查，防止大数溢出被限幅隐藏。消息没有航向字段，预览使用调用者提供的可信航向参考。垂向目标仅展示，没有接入原高度控制器。

`Session` 的第一个错误会保留到 `begin_attempt()`。这是离线预览会话的重建机制，不是清除飞机故障的接口。整个模块没有生成权限租约、PX4 控制请求或最终动力输出。

## 阅读时记住这几个单位和术语

| 代码中的名字 | 人话含义 |
| --- | --- |
| `received_at` / `now` | 本机 monotonic 时间，单位秒，用来判断接收间隔 |
| `stamp_ns` / `ros_now_ns` | 测量时间和本机 ROS 时间，单位纳秒；只有时钟关系已确认才能比较 |
| watermark | 已通过检查的最大序号或时间；非法消息不能推进它 |
| `reset_counter` | 所属模块的重置周期；制导端和估计端各自独立 |
| `cache` | 有有效期的当前缓存，历史记录不能代替它 |
| `control_authority=false` | 该结果只有诊断或预览用途，没有飞行控制权限 |

复核应同时看既有回归和修改前后相同行为的差分结果。本轮结果另记入可读性整理证据；主机验证不代表 ARM64、真实传感器或实机飞行验收。
