# FC01 双串口方案与只读核查（2026-11-05）

本轮锁定最终硬件拓扑，新增独立的被动检查器；**第二链路尚未启用，尚未实现双链路分流或带宽扩容**。没有改现用 Agent、服务、启动入口、控制器、运行 YAML、飞控参数或固件。倾角策略调整不包含在本次通信变更中。

## 1. 唯一有效的硬件拓扑

| 用途 | Orange Pi Zero 3W V1.2 | DAMIAO FC01 | 状态 |
|---|---|---|---|
| 现用主链路 | **UART2，`/dev/ttyS2`，115200**；TX Pin11 / PB0，RX Pin13 / PB1 | **UART6，RX6 / TX6** | 用户确认正在使用；原 MicroXRCEAgent 完整保留 |
| 新增候选链路 | **UART6，候选 `/dev/ttyS6`**；TX Pin24 / PE0，RX Pin23 / PE1 | **UART4 / TELEM3，RX4 / TX4** | 未启用；波特率未配置 |

新增接线为 Pin24 TX → FC01 RX4，Pin23 RX ← FC01 TX4，双方共地（香橙派可用 Pin25）。接线前须确认两端接口电平、实物针序和 UART4 空闲状态；本轮未进行电气测量或接线。

两台设备的 UART 编号和 Linux/NuttX 设备名分别核对，不能互换。旧的 USB 转 TTL 候选以及不同端口方向的草案已经被此拓扑取代，不作为交付方案。

## 2. 硬件资料与实际运行证据分开

香橙派官方 [Zero 3W V1.2 引脚图](http://www.orangepi.org/img/zero3w/details/24.webp)与[官方服务页](http://www.orangepi.org/html/hardWare/computerAndMicrocontrollers/service-and-support/Orange-Pi-Zero-3W.html)链接出的 [OPI ZERO 3W V1_2 原理图](https://drive.google.com/file/d/1layhtSvMpQo-z_iMJjNfNVvhPhObpsvW/view)一致：原理图第18页确认物理针脚，第9页确认 PB0/PB1 的 UART2、PE0/PE1 的 UART6 功能。这支持上述香橙派硬件引脚声明，不能证明现场设备树已经启用 UART6。

官方 [Zero 3W 板级 DTS](https://github.com/orangepi-xunlong/linux-orangepi/blob/orange-pi-6.6-sun60iw2/arch/arm64/boot/dts/allwinner/sun60i-a733-orangepi-zero3w.dts)包含对应引脚组；读取的版本将 UART2、UART6 均设为 disabled。官方 [SoC DTSI](https://github.com/orangepi-xunlong/linux-orangepi/blob/orange-pi-6.6-sun60iw2/arch/arm64/boot/dts/allwinner/sun60iw2p1.dtsi)中 serial2/serial6 分别指向地址 `0x02502000` / `0x02506000`。这是源码默认值，**不能据此改动已正常工作的 UART2**。

官方 [UART 驱动](https://github.com/orangepi-xunlong/linux-orangepi/blob/orange-pi-6.6-sun60iw2/bsp/drivers/uart/sunxi-uart-ng-core.c)依据 serial alias 编号注册设备，设备前缀受内核配置影响，存在 ttyS、ttyAS 分支。现场需要串起 `设备节点 → sysfs driver/of_node → 运行中 DT alias/node → pinctrl` 才能确认候选映射。板型字符串也不是唯一证据：读取的官方 Zero3W DTS 自身仍包含 orangepi-4-pro compatible，应结合实物丝印、model、SoC 和引脚资料核对。

当前开发机为 x86，未获得香橙派 SSH 或 FC01 控制台连接。下列现场项目全部为 **NOT_OBSERVED**：`/dev/ttyS6` 是否存在、活动设备树、实际 pinmux、驱动绑定、串口占用、电平、FC01 UART4 占用、当前刷入固件身份和当前流量。不能以开发机报告代替设备验收。

## 4. 香橙派先做这些只读检查

把 [uart_preflight.py](../uart_preflight.py)复制到香橙派任意普通目录，使用现有 Python3 运行即可；无需 ROS、安装依赖或停止原服务。输出目录必须尚不存在：

```bash
python3 uart_preflight.py --output "$HOME/FC01_UART6_preflight_20261105_01"
```

工具默认检查候选 `/dev/ttyS6`，并对照现用 `/dev/ttyS2`，生成 `report.json`、`report.txt`。重复采集时换一个新的目录名。工具仅读取系统元数据；不会打开任何串口，也不会调用 termios、写 overlay、挂载 debugfs、启停服务或连接控制 IPC。

检查内容：字符设备及主次设备号、是否与主链路同一设备、绑定驱动及 of_node、活动 DT alias/节点/父节点状态、pinctrl phandle 与引脚、内核 console、getty 和可见进程占用。默认 ttyS6 还核对 serial6、uart6、PE0/PE1 的一致性。`systemctl show` 与 `fuser --` 是唯一外部命令，均有4秒超时；不调用 sudo。

| 报告状态 | 含义 |
|---|---|
| `not_ready` | 已看到冲突，例如已占用、console、DT disabled、映射不符或与主设备重合 |
| `unknown` | 缺设备、缺权限、缺工具、无绑定或证据无法解释；不是“可用” |
| `eligible_for_manual_review` | 被动软件证据齐备，仍需人工核对实物、电平及端到端通信 |

最高等级始终只表示可进入人工复核，`hardware_validation` 恒为 `NOT_PERFORMED`。fuser 仅能看见当前用户可见的进程，不能证明全局独占；boot配置文字也不能证明某个overlay已加载。工具不验证 U-Boot 阶段是否占用或输出字符。若权限导致 unknown，先保留原报告，按具体缺项补只读证据，不能将其改写成通过。

必要时人工只读补充已有 debugfs 的 pinctrl owner/handles、内核配置和串口服务；不为采集而挂载或改配置。UART6 未启用时先回传报告与系统镜像版本，再依据实际 BSP 选择后续启用方法。本轮不给未经核实的 overlay 名称或启动指令。

## 6. 后续源码修改方案，当前未实施

在保留一个原生 DDS 客户端与一个 Agent 的前提下，建议先评估**独立、仅输出的辅助遥测桥**。这不是当前固件已有功能，也不是一个可直接启用的第二 DDS 串口。

| 修改位置 | 必要工作与约束 |
|---|---|
| 新增 PX4 辅助输出模块（拟定 fc01_aux_tx）及板级构建项 | 仅订阅白名单 uORB 输出；独占候选 UART4；非阻塞发送、有界队列与带宽预算。不创建任何控制 uORB 发布者、不处理运动指令或解锁命令。启动参数、缓冲/DMA和资源需另行验证。 |
| 新临时传输协议 / 主机接收器 | 定义同步标记、版本、schema/类型、长度上限、序号、测量时间戳、重置/质量/有效性和CRC；处理短写、拆包、乱序、重连。短写时保留完整帧缓冲和精确偏移，续传后缀，本帧完成前不插入下一帧；只能直接丢弃尚未开始发送的整帧。发送超时须报告故障并重新同步，不能无条件重发整帧。主机只发布到 `/fc01/aux/out/...`，不写 `/fmu/in` 或控制IPC。 |
| 主 DDS 话题分区（仅在后续明确授权后） | 先核对 ROS 图与每个消费者，再从主 DDS 输出中移除批准迁移的非关键话题，同时更新 dds_topics.yaml / dds_rate_profile.json / 生成验证；主输入和所有权不复制。 |
| 自动化验证与构建 | 用录制数据、伪终端或注入传输验证双向背压隔离、损坏/短写/重连；检查无控制实体、无重复话题、FLASH/RAM/栈与负载。实际固件构建、部署及设备验收另安排。 |

**只在新链路复制遥测，并不会降低原链路负载。** 若持续要求原链路配置和话题完全不变，当前只能增加独立观察能力，不能声称已经分摊它的负载。实际扩容必须有新增业务走新链路，或在后续授权范围内迁移已核准的输出话题。

当前控制器依赖的9类主反馈暂时全部保留原 DDS：vehicle_attitude、vehicle_local_position、**vehicle_status_v1**、vehicle_land_detected、battery_status、failsafe_flags、vehicle_command_ack、manual_control_setpoint、manual_control_switches。若后续要求将所有控制反馈迁到辅助链路，还必须增加控制侧适配、完整性与时钟验证，并重新验收整个权限/故障路径；本轮没有完成或启用这种迁移。

若以后必须让第二链路也使用 DDS，需设计多实例客户端或单客户端多传输，以及对应 Agent 传输架构。多客户端各有独立session，同一Agent下使用不同非零key；单客户端多传输须明确原session的传输归属。两种方案都要定义互斥话题集合、单份控制订阅、时间同步、重连与队列归属。原模块加一个端口参数或复制实例都不够；在当前“不启动第二 Agent”的限制下，不能用多开 Agent 充当实现。

## 7. 控制发布源和健康监控

本工程源码规定的外部飞行设定值路径为原生 Runtime → 最终发布复核 → 现用 DDS 主链路。现场是否只有一个有效发布源，仍须ROS端点图和实际部署证据核实。保留现有发布者独占、RC新授权、接管、失效退出和PX4保护；新的被动检查器不导入飞控控制模块，不创建ROS发布者。辅助链路设计中禁止 `/fmu/in/*`、VehicleCommand和控制IPC，任何重连都不能新建第二控制源或抢回权限。

辅助链路的后续状态设计为 `DISABLED → WAIT_HARDWARE → WAIT_FIRST_FRAME → HEALTHY → DEGRADED / STALE / FAULT`。本轮检查器并不实现运行中通信或飞行故障状态机。

| 运行监控项（待实现） | 处理规则 |
|---|---|
| 各链路独立收发字节、有效帧、CRC错误、序号缺口、队列深度/丢弃、重连代次 | 独立进程/线程与有界队列；辅助堵塞不得阻塞20Hz主控制循环 |
| 接收单调时钟、来源测量时间、逐话题推进、重置计数 | 收到字节、收到心跳、收到新测量分别记录；坏帧/重复数据不刷新测量有效期；飞控启动时间不能直接与Unix时间相减 |
| 辅助链路超时 | 依实测频率与抖动定标；工程提案 `T_link=max(3/f_heartbeat, 0.5s)` 仅是待验证起点，逐话题另设过期，不是本轮生效参数 |
| 断链、来源重启、时间回退 | 失效旧缓存和重连前批次，重新建立时间关系；连续有效且推进的反馈后再恢复健康 |
| 辅助链路失效 | 标记辅助数据无效；不清空主状态、不自动替换控制反馈、不发虚假心跳维持Offboard |
| 主链路失效 | 保持已有控制器与PX4处理；辅助在线不能充当主链路健康证明或自动接管依据 |

仓内配置的姿态/位置超时0.5s、status/land/flags 2.5s、电池新鲜度1s、循环停滞0.3s等基线未修改。辅助超时方案须独立验收，不能借新增链路放宽原保护。

## 8. 容量与验收依据

115200、8N1时，单方向上限为 `115200 / 10 = 11520 B/s`。全双工是每方向分别预算，不能把双向字节相加与单方向上限比较；CDR尺寸还没有计入XRCE分帧/转义、会话、可靠重传、时间同步及突发。新增串口实际收益取决于迁移的负载、两端处理能力和独立队列，不直接等于两条波特率相加。

本地 diagnostic profile 的姿态/位置间隔50ms、电池500ms、部分IMU/GPS/里程计1000ms；其他状态/ACK/RC的10ms是转发上限，并不是实测100Hz。候选非关键话题已经限流，实际可卸载量可能很小。历史超载模型不能替代当前窗口测量，见[历史通信审计](COMMUNICATIONS_AUDIT_20261103.md)。相机与外置IMU在香橙派本地产生的数据留在本机处理，不因接入视觉而自动经过飞控串口。

最小设备证据为：①本工具的两个报告；②上述FC01只读输出和固件来源；③原 [navigation_collect.py](../navigation_collect.py) 同窗报告（必要时10秒被动ROS窗口），包含实际服务/二进制/runtime/SDK/Domain/QoS、关键话题频率及测量年龄；④若需要判断实际线速/排队，则另取得该窗口现有串口驱动/固件统计或被动逻辑分析记录。缺少第④项时不能把ROS字节估算称作线上实测。

离线验证覆盖检查器的只读边界、模拟设备树/驱动/引脚/占用/console/异常输入以及x86实际执行；它不验证真实串口收发、双链路分区、香橙派驱动或飞行性能。验证命令与本轮最终结果见 [验证记录](evidence/20261105_uart_validation.md)。
