# FC01 双串口映射审计与只读核查（2026-11-06）

## 结论先行

本轮没有把任何端口重新配置，也没有启动第二个 MicroXRCEAgent。当前证据只能得出以下结论：

* FC01 现场 NSH 日志确认 uXRCE-DDS 当时启动在 **NuttX `/dev/ttyS3 @ 115200`**，`UXRCE_DDS_CFG=103`，会话已连接。
* 与该固件提交对应的本地板级源码把 `/dev/ttyS3` 映射为 **STM32 UART4、PX4 逻辑 TELEM3、PB8/PB9**。
* 用户最新实物记录认为现用线束是 Orange Pi `/dev/ttyS2` ↔ FC01 **USART6 / RX6/TX6**。这与上面的运行端点/源码链冲突，**当前不能把物理线束标为已验证，也不能把 UART4 标为可用**。
* 用户报告 Orange Pi 的 `/dev/ttyS6` 已出现且由 `uart-ng` 驱动，但候选线尚未做回环或 FC01 端到端测试。它保持 **`UNRESOLVED_DO_NOT_ENABLE`**。

冲突可能来自接插件半边或针序认错、板卡版本与手册不一致，或现场刷入的镜像并非本地带未提交修改的构建；当前没有证据可以在这些假设中选择一个。不得通过改 `UXRCE_DDS_CFG`、改接线或添加第二 Agent 来强行让记录一致。

## 2. 完整的源码映射链

以下是对 `/home/jikl62/FC01_DDS_V3_NATIVE_BUILD` 的源码审计结果。该树 HEAD 与现场报告的 PX4 hash 相同，NuttX 子模块为 `886acbbdb4f061e5c0ce1a76afbcfa7cb7df9849`；但树存在未提交定制，且 hash 不能证明现场 `.px4` 的字节身份。

| PX4 逻辑选择值 | PX4 逻辑名 | NuttX 设备 | STM32 外设 | RX / TX GPIO（AF） | 波特率参数 | 手册接口含义 |
|---:|---|---|---|---|---|---|
| 101 | TELEM1 | `/dev/ttyS1` | USART2 | PD6 / PD5（AF7） | `SER_TEL1_BAUD` | TELEM1 四针：TX3、RX4 |
| 103 | TELEM3 | `/dev/ttyS3` | UART4 | PB8 / PB9（AF8） | `SER_TEL3_BAUD` | 共用八针接口的 TELEM3 半边：TX3、RX4 |
| 6 | `URT6` / UART 6 | `/dev/ttyS5` | USART6 | PC7 / PC6（AF7） | `SER_URT6_BAUD` | 同一八针接口的物理 TELEM4 半边：TX7、RX8 |
| 104 | TELEM4 | `/dev/ttyS6` | UART7 | PE7 / PE8（AF7，板级注释 TX 为 NC） | `SER_TEL4_BAUD` | ESC telemetry；不是物理 TELEM4 半边 |

这里有一个容易造成误接的名称冲突：**接口丝印“TELEM4”的 USART6 半边使用 PX4 选择值 6（`URT6`），而 PX4 逻辑 `TELEM4`/104 在这套源码中是 UART7/`ttyS6`。** 不能从物理接口名推导参数值，也不能把 Orange Pi 的 `/dev/ttyS6` 当成 FC01 的 `/dev/ttyS6`。

源码证据包括：

* `boards/damiao/dm-fc01/default.px4board:3-8`：端口路径为 `URT6=/dev/ttyS5`、`TEL3=/dev/ttyS3`、`TEL4=/dev/ttyS6`。
* `boards/damiao/dm-fc01/nuttx-config/include/board.h:366-396`：USART2 为 PD6/PD5，UART4 为 PB8/PB9，USART6 为 PC7/PC6，UART7 为 PE7/PE8。
* `nsh/defconfig:204,217-256` 与生成的 `.config:346-354,394`：UART4、USART6、UART7 均启用，`CONFIG_STM32H7_SERIAL_DISABLE_REORDERING=y`；串口数组按硬件编号注册，所以 NuttX `ttyS` 序号不能按物理连接器名称猜测。
* `stm32_serial.c:1469-1510,3903-3924`：`g_uart_devs` 按 USART/UART 编号注册，随后将其注册为 `/dev/ttyS*`；没有发现交换 UART4/USART6 的板级初始化代码。
* 生成的 `etc/init.d/rc.serial_port:1-55` 和 `rc.serial:200-209`：选择值 103 设置 `/dev/ttyS3`，选择值 6 设置 `/dev/ttyS5`，选择值 104 设置 `/dev/ttyS6`；uXRCE 使用单一 `UXRCE_DDS_CFG` 选择一个端点。
* `hardware/stm32h7x3xx_pinmap_legacy.h:1481-1513`：UART4 PB8/PB9 与 USART6 PC7/PC6 均为 AF8/AF7 定义；这只是 MCU 复用证据，不替代接口针脚和电气核验。
* `rc.board_extras` 中的 “DShot telemetry is always on UART6” 后面是注释掉的示例，不是当前占用证据。

制造商资料（需再核对实物板 revision）给出的八针排列为：1 GND、2 +5V、3 UART4 TX/PB9、4 UART4 RX/PB8、5 GND、6 +5V、7 UART6 TX/PC6、8 UART6 RX/PC7。资料明确区分物理 TELEM4 半边与 PX4 逻辑 TELEM4。固定版本资料及校验值记录在 `docs/evidence/20261106_uart_mapping_audit.json`；实际板 revision 尚未验证。

## 3. 运行端点与冲突分析

现场日志中的 `Starting UXRCE-DDS Client on /dev/ttyS3` 是当前最直接的运行证据。结合本地源码，它指向 UART4/PB8-PB9，而用户的最新线束记录指向 USART6/PC7-PC6。因此：

* 不把“`UXRCE_DDS_CFG=103` 的标准标签 TELEM3”单独当成物理接口确认；它只能说明参数选择和该次启动设备。
* 不把 `MAV_0_CONFIG=101`、`/dev/ttyS1` 或 USB MAVLink 状态当成 UART4/UART6 空闲证明。传感器、GPS、RC、DShot、MAVLink 和手动启动模块都可能在参数之外占用串口。
* `uxrce_dds_client status` 只显示 serial、session、ping 和 payload 统计；设备名/波特率要以启动日志为准。用户的 `Payload tx=6614 B/s` 不是串口线上完整帧字节，也不是剩余容量测量。
* 当前 uXRCE 客户端是单实例、单 `UXRCE_DDS_CFG`、单 Agent 传输；本地源码没有可以直接把话题分到第二串口的并行配置。新增 Linux Agent 也不会自动形成第二个飞控传输源。

## 5. 只读核查步骤

当前用户已经提供了第一轮 NSH 和第二轮 MAVLink 摘要，不需要为重复采集而重启 Agent。若冲突仍需现场收敛，在 QGroundControl 的 MAVLink Console 中逐条执行并保存原始输出：

```text
ver all
param show UXRCE_DDS_CFG
param show UXRCE_DDS_DOM_ID
param show UXRCE_DDS_KEY
param show SER_TEL3_BAUD
param show SER_URT6_BAUD
param show SER_TEL4_BAUD
param show MAV_0_CONFIG
param show MAV_1_CONFIG
param show MAV_2_CONFIG
uxrce_dds_client status
mavlink status
ps
dmesg
```

从 `dmesg` 保留含 `Starting UXRCE`、`init serial`、`Conflicting config`、`mavlink` 的行。若固件允许只读 `cat`，再保存但不要执行或 source：

```text
cat /etc/init.d/rc.serial_port
cat /etc/init.d/rc.serial
```

找出正在运行的 uXRCE PID 后，可尝试只读 `cat /proc/<PID>/cmdline` 和 `cat /proc/<PID>/group/fd`，记录实际打开路径；缺少 `/proc` 或权限不足时记为未知。 `ps`/FD 只能补充软件所有者，不能证明接插件针脚连续性。

最小的下一批证据是：

1. 保持现用链路不变，记录实际八针编号、线束 TX/RX 和板上 revision 照片或手册版本；
2. 在不启动第二 Agent 的前提下，给出 uXRCE 进程 FD 与 `rc.serial_port` 的只读结果；
3. 若仍冲突，再提供现场刷入 `.px4` 的构建来源/校验值；
4. 只有身份和占用一致后，另行安排断电状态下的候选 UART6 ↔ UART4 回环与端到端测试。

QGroundControl 参数页面本轮只搜索、查看、导出，不点击写入；不修改 `UXRCE_DDS_CFG`、`SER_*_BAUD`、`MAV_*_CONFIG`，不启动第二 Agent，不刷写固件。

## 6. Orange Pi 只读检查器

将 `uart_preflight.py` 复制到香橙派普通目录，用新的输出目录运行：

```bash
python3 uart_preflight.py --output "$HOME/FC01_UART6_preflight_20261106_01"
```

默认只检查 Orange Pi 候选 `/dev/ttyS6`，并以 `/dev/ttyS2` 作对照。检查器读取字符设备、sysfs/设备树、pinctrl、console/getty 和可见占用；外部命令仅限带超时的 `systemctl show` 与 `fuser --`。它不会打开串口，不会做回环，不会写设备树，不会停止 `fc01` 服务。

用户已报告：删除 `spi3-cs0-cs1-spidev` overlay 后 UART6 成功出现并绑定 `uart-ng`。本轮不重复修改这个设备树修复，也不把用户终端结果伪装成开发机实测；检查器报告与用户结果分别保存。

报告状态 `eligible_for_manual_review` 只代表被动软件证据齐全；`hardware_validation` 仍为 `NOT_PERFORMED`。 `unknown` 不是可用，`not_ready` 不能通过重试绕过。

## 7. 第二串口的后续开发边界

本轮不实现双 DDS、不迁移话题、不创建第二控制源。未来若证据确认一个空闲物理端口，仍需先选择并验证一种方案：

* 仅新增非控制遥测桥：独占第二端口，定义版本、长度、序号、时间戳、质量/重置标志、CRC 和有界队列；主控制 DDS 保持单一来源。
* 迁移经过批准的非关键 DDS 输出：同步修改话题表、频率 profile、Agent 传输和所有消费者，验证不会复制控制输入或反馈。
* 多实例 DDS 客户端或多传输方案：需要 PX4 固件改造、独立 session/key、话题互斥、时间同步与重连归属；当前固件没有现成开关。

任何辅助链路失效都只能标记辅助数据无效，不能发虚假心跳、替换主控制反馈或抢回权限。现有 RC 接管、发布者独占、PX4 失效保护和 20 Hz 控制链路保持不变。
