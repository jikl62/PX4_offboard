### OVN-01 如何复现和验证

原始严格编译命令缺少链接注入参数，报 `__real_fcntl` / `__real_write` 未定义，退出 1。新增回归使用真实旧入口、真实日志资源测试和真实 g++；原两个入口均失败，修复后均通过。普通程序不获得 wrap 参数，普通程序退出 17 时仍立即终止入口，不能继续执行后续步骤。

最终还实际运行了 `bash native/scripts/test.sh`：全部当前 C++ 测试、历史反例解释器、消息 API 编译夹具和 41 项 native Python 测试完成，退出 0。历史反例中的预期 assertion abort 由原回放器解释，不当作当前正向失败，也不删除原断言。另一个 R62 入口末尾所需的历史 CSV 仍缺失；本阶段没有伪造数据或声称完整 R62 历史回放通过。

### OVN-08 如何复现和验证

原 main 在 `node = DiagnosticNode()` 的完整构造结束前拿不到对象。假 ROS 在基类已成功、参数或订阅等配置失败时，实际记录为 `init → create → shutdown`，缺少显式 `destroy`；destroy 抛错还会跳过后续 shutdown。这里确认的是应用层清理缺陷，没有证据把它扩大成永久 DDS 泄漏或真实飞行故障。

修复后的顺序为：当前回调返回 → 终态证据（仅配置完整后）→ 移出 executor → destroy → 自有 Context shutdown → 恢复信号处理器。每项清理失败仍尝试后续动作；业务原错不被覆盖；没有业务错误时，首个清理错误向外传播。原先吞掉的退出文件错误现在会保持可见，这是独立功能修复，不属于行为等价注释。

15 项生命周期测试覆盖配置/订阅/定时器/首快照失败、重复初始化、原异常链、多项清理失败、外部关闭、信号交错及 20 次重复启动退出。基类构造本身未返回时没有完整 Node 供应用显式销毁；没有证明底层任意半构造异常均立即释放。100 ms 只是 executor 空闲等待参数，不是硬实时退出上限。
