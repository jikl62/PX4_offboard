# 打开源码后的中文阅读路线

这里的“起飞”分五层：飞控测量事实、人工/任务授权、控制计算、真实本地发布、PX4采用与物理响应。代码中的一个 `true` 通常只证明其中一层。

## 先认识源码里的对象

| 源码写法 | 在本工程里的具体意思 |
|---|---|
| `Config c` / `config_` | 本次参数值/对象持有的参数，动作开关与实际授权不同 |
| `Feedback s` / `Snapshot s` | 同轮整理的飞机观测；没有新鲜度证据时数值存在也不能授权 |
| `Output out` / `output` | 计算计划；`publish=true`还没越过最终发布门 |
| 成员名尾部 `_` | 本工程命名习惯：该状态随对象跨调用保留，并非C++的特殊关键字 |
| `const T&` | 借用已有对象且不通过此引用修改；不是复制，也不延长被借对象的一般寿命 |
| `T*` / `p->x` / `*p` | 指针、访问所指对象成员、取得所指对象；可空指针必须先判空 |
| `unique_ptr<T>` | 对象的唯一所有者；销毁或reset时释放对象，借用引用不能比所有者活得久 |
| `optional<T>` | 有值或无值；先判空再 `*q`，空结果不等于单位四元数 |
| `[this]` / `[&]` | lambda保存节点指针/借用局部量；需看执行是同步完成还是存到未来回调 |
| `&&` / `||` | 左到右短路；保护判空、时序比较、首错判断，不能改成按位运算 |
| `return {}` | 返回默认空结果，不撤销函数前面已经发生的状态写入或外部发布 |
| `throw` / `catch (...)` | 异常传播；边界里的裸throw保留原始发布错误，不把半包算成功 |

`f`是Node中的`fc01`命名空间别名，`v`通常是通用速度库别名。`q`可能是四元数，在测试里也可能是夹具名；不能按一个字母全局猜意义。

## 四种时间先分开

1. `now/steady/received`：本机单调秒，用于周期、租约和接收进展。
2. 消息 `timestamp`：源消息微秒，用于消息推进和已核验同步域内的因果关系。
3. `timestamp_sample`：原始测量微秒，新外壳可能包装旧测量，不能拿新外壳给旧测量续鲜。
4. `armed_time`：PX4自身启动相对微秒，只与同源历史值比较，不与ROS/主机时刻直接相减。

名字叫`stamp`不自动证明已同步；`source_host_stamp`也须配合有效位。整数源戳先比大小再相减，避免无符号数把负差绕成大正数。

## 高度怎样变成推力

先读 `attitude_types.hpp`，再读 `vertical_controller.hpp` 的 `step`。

- PX4世界NED：Z朝下，`z/vz`单位m/m/s。地面`z0=2`、飞机`z=0.5`，相对向上高度为`2-0.5=1.5m`。
- 控制器使用向上速度，故`speed=-vz`。`vz=-0.2`意味着向上0.2m/s。
- 高度误差乘Kh（1/s）变成速度目标（m/s），再加轨迹速度前馈并限制爬升/下降幅值。
- 速度误差乘Kv（s/m）形成无量纲推力修正；积分先试算，再判断是否会继续顶住饱和/变化率约束。
- 悬停基准+比例+已接受积分形成推力；临时起飞上限、物理限幅、slew共同保留制动余地。
- 内部推力是向上正幅值，写到机体FRD消息时升力为负Z；0.5不是0.5N，也不是已离地证明。

不要改写数学表达式的乘加顺序。即便纸面代数相同，double舍入和状态提交时点仍可能不同。

`vertical_feedback_guard.hpp`检查的是同一估计器内部一致性：`vz-z_deriv`仅告警；z位移与z_deriv梯形积分的既有硬拒绝仍保留。它不切高度源，也不能证明真实高度没有共同漂移。

## 人工 RC 到1.5m平台的逐层执行

| 阅读点 | 本层发生的事 | 仍不能推断的事 |
|---|---|---|
| `RcNavigationStart::step` | 未解锁安全地面、新源样本与实际零流提交形成READY | READY不是人工同意或电机解锁 |
| `step_wait_navigation` | 新CH5边沿+RC原因armed状态绑定同次armed_time，再配新导航档和实际Offboard | 仅遥控档位变化不是PX4已进入Offboard |
| `Core::step` 的 ArmedGround/ThrustRamp | 锁参考、地面观察、调度推力，分别累计检测器与真实上升证据 | 有推力或一个!landed都不证明离地 |
| Ascend/HeightHold | 受限高度轨迹进入闭环并到平台 | 计划通过不等于本地已发送或PX4已执行 |
| `Runtime::step` | 分派路线、维护命令事务和期限 | ACK不自动证明姿态、上锁或落地 |
| `SystemNode::tick` | 消费离散事件、计算计划、重采样最终上下文、调用sink、回记提交 | ROS publish返回不等于PX4采用 |
| Descent/Landed/RequestDisarm | 新地面证据后请求上锁并用独立新状态终结 | landed单帧、旧ACK或默认armed=false均不够 |
| Safety/RC恢复 | 新未解锁地面证据满足后重新准备 | 不会自动重新解锁或夺回人工接管后的控制权 |

Core阶段使用连续`else if`以及少量有意的同帧继续执行：不要把每个`enter`都理解成“下帧才处理”，也不要为了短函数统一插入return。源码各段已解释哪些写入在当帧后续判断中生效。

## 到最后发布时再检查一次

Node先处理中间危险事件，健康末帧不能将它们覆盖。Runtime/Core形成计划后，计划含姿态发布时走：初始上下文→编码→target前重查→target返回→heartbeat前重查→heartbeat返回。只有本地完整配对后才允许与其关联的动作和提交确认。

两个sink不能原子提交：target已发而heartbeat拒绝属于部分发布，要留下证据并传播错误。无姿态发布计划的独立动作没有这个配对前置要求，仍必须通过各自的最终权限/地面/事务门。

建议在VS Code按顺序跳转：`SystemNode::tick` → `Runtime::step` → `Core::step` → `VerticalController::step` → `publish_attitude_resampled` → `confirm_attitude_command_publication` → `Runtime::ack`。用符号导航读函数，保留每个函数前的合同注释；不要只从日志里的`FAULT`倒推整条控制链。
